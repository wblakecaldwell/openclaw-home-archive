# Architecture — OpenClaw Personal Archive

## 1. Problem statement

Personal records and durable evidence are unusually messy and long-lived. Useful information arrives through
casual messages, photos, PDFs, receipts, labels, business cards, and later corrections.
Months or years later the user wants an answer plus the original evidence.

Examples:
- purchases, receipts, and invoices
- appliance brand/model/serial information
- warranty documents and user manuals
- vehicle and bicycle records and serial numbers
- contractor identities and business cards
- construction/service dates
- paint labels and finishes
- HVAC filter sizes
- maintenance history
- photos of packaging/model labels
- personal projects and measurements
- belongings and durable assets

Ordinary conversational memory is not sufficient because it may summarize, compact, merge,
or forget details and is not an evidence store. Personal Archive therefore separates durable
records and evidence from conversational memory.

## 2. Goals

The system should:

- accept messy natural-language capture;
- preserve original evidence;
- accumulate information onto persistent real-world entities;
- retain provenance and history;
- make corrections and deletion safe;
- retrieve a small relevant subset instead of flooding model context;
- work with relatively small/local language models;
- remain inspectable on disk;
- survive rebuilding derived indexes/projections;
- support convenient Apple Photos browsing without making Photos authoritative;
- avoid requiring the user to maintain categories or schemas manually.

## 3. Non-goals

At this stage the project is not intended to:

- replace a general document-management platform;
- make Apple Photos the canonical database;
- put the archive in Git;
- depend on OpenClaw's ordinary conversational memory for durability;
- require a cloud model;
- require the user to issue database commands;
- automatically make aggressive entity-linking decisions when ambiguous;
- permanently destroy data by default.

## 4. Layered architecture

### Layer A — authoritative filesystem archive

Configured root (`PERSONAL_ARCHIVE_ROOT` environment variable):

    <archive-root>

`<archive-root>` is a documentation placeholder for the chosen absolute archive path
outside this repository. Configure the variable in the environment running the CLI,
including OpenClaw-launched commands. Changing it selects a directory; it does not
migrate existing data.
The canonical default location is `~/Documents/OpenClaw/PersonalArchive`. Installation stores an explicit user choice
under `skills.entries.personal-archive.env.PERSONAL_ARCHIVE_ROOT` through OpenClaw's config
CLI. The Python archive CLI requires the environment variable at execution time;
importing the module and requesting CLI help do not require configuration.

This layer owns durable records, attachments, provenance, and event history.

It must be useful even if all embeddings, model memory, and Photos projections disappear.

### Layer B — current views and search/indexing

Human/model-readable Markdown plus deterministic search/indexes make the archive practical
to retrieve.

A local embedding index may be added/used as a derived accelerator. It is disposable and
must be rebuildable from Layer A.

The design has discussed local Nomic embeddings, but the archive format must not depend on
a particular embedding provider/model.

### Layer C — Apple Photos projection

Selected image attachments can be imported into a regular album named `Personal Archive`.

Photos exists for convenient human browsing. It is a materialized view and can be rebuilt.

## 5. Filesystem model

Conceptually:

    <archive-root>/
    ├── README.md
    ├── records/
    │   ├── ARCHIVE-20260920-0001/
    │   │   ├── record.md
    │   │   ├── metadata.json
    │   │   ├── events.jsonl
    │   │   └── attachments/
    │   └── ...
    ├── trash/
    └── state/
        └── sequence.json

### `metadata.json`

Represents current structured state. Expected concepts include:
- schema version
- stable record ID
- title
- summary
- event date where appropriate
- created/updated timestamps
- deleted state
- keywords
- current/active facts
- attachment references
- notes

The exact current schema is defined by the implementation; documentation should follow code
rather than invent incompatible fields.

### `events.jsonl`

Chronological durable history. This makes mutation history auditable and allows current
views to evolve without erasing what happened.

### `record.md`

A concise readable representation of current state. It is useful for humans, local model
context, grep/search, and future indexing.

It is not the only authoritative representation.

### `attachments/`

Contains copied originals. Derived extraction does not replace the original.

## 6. Identity

### Entity IDs

Stable entity IDs use an `ARCHIVE-` prefix. Current implementation generates forms such as:

    ARCHIVE-20260920-0001

IDs are generated by deterministic code. They are opaque to the conversational layer.

### Attachment IDs

Stable attachment IDs use an `ARCHIVE-ATTACH-` prefix. They are likewise generated by code. Current implementation generates forms such as:

    ARCHIVE-ATTACH-20260920-0001

Attachment IDs are useful outside the filesystem, particularly as Apple Photos metadata
for reconciliation.

## 7. Entity lifecycle

### Create

Create a new persistent entity when the user introduces a new item/project/asset/etc.
and there is not a confident existing match.

### Add

Later evidence should attach to the existing entity when association is sufficiently clear.

Example:
1. "We had the back deck built today by Joe from Example Decks."
2. Months later: "Here's Joe's business card. He's the guy who built our deck."

The business card should normally be added to the existing deck record.

### Update

A correction creates a new current value while preserving useful history/provenance.

Example:
- previous purchase price: $119
- user: "The toaster actually cost $129."

Current state becomes $129 while history can explain the change.

### Remove

Removal should generally be reversible/history-preserving.

### Delete

Entity deletion should be soft by default: mark deleted and/or move to archive trash.
Permanent purge is a distinct destructive action requiring explicit confirmation.

### Merge

Duplicates are expected because conservative matching is intentional.
If the user says two records refer to the same real-world thing, merge into a canonical
entity while preserving facts, events, attachments, and provenance.

## 8. Provenance model

A fact is more useful when the system can explain why it believes it.

Examples:

    key: model
    value: BTA820XL
    source: IMG_1036.jpg
    confidence: high

    key: deck_completion_date
    value: 2026-09-20
    source: user
    confidence: high

Source may point to:
- user statement
- attachment
- derived extraction from an attachment
- another explicit archive event

Original evidence remains available so a user can inspect it if extraction was wrong.

## 9. Natural-language orchestration

Natural-language orchestration is divided across an intentional two-agent boundary:

```
User / iMessage
      │
      ▼
main agent
  - Detects Personal Archive intent
  - Collects user request and attachment paths
  - Resolves conversation-dependent references (e.g. "it" -> "the bike")
  - Delegates via sessions_spawn(agentId="archivist", context="isolated", ...)
  - Relays child relay_message directly; never supplements from memory
      │
      │ sessions_spawn (agentId: "archivist", context: "isolated", mode: "run")
      ▼
dedicated agent: "archivist" (Archivist)
  - Isolated workspace (~/.openclaw/workspaces/archivist)
  - Zero main agent chat history or conversational memory
  - Performs domain interpretation:
      • normalizes relative dates against invocation timestamp
      • extracts durable facts from prose and attachments
      • attributes provenance (source, confidence)
  - Invokes python3 {baseDir}/scripts/personal_archive.py ...
  - Returns structured response envelope with pre-rendered relay_message
      │
      │ CLI execution
      ▼
Authoritative Filesystem Archive
  - ~/Documents/OpenClaw/PersonalArchive
```

### Division of responsibilities

1. **Main agent (`main`)**:
   - Resolves conversation dependency ONLY: pronouns ("it", "that guy") that cannot be understood without prior conversation turns.
   - Does NOT interpret dates (leaves "yesterday", "last week" as original wording).
   - Does NOT extract facts from prose or attachments.
   - Passes original request, resolved context, invocation timestamp, and attachments.

2. **Dedicated agent (`archivist`)**:
   - Operates in clean, isolated context (`context: "isolated"`).
   - Performs domain interpretation: resolves relative dates against invocation timestamp, extracts facts, attributes provenance.
   - Issues deterministic CLI commands.
   - Never fabricates `ARCHIVE-...` or `ARCHIVE-ATTACH-...` identifiers.
   - Formulates a complete, user-facing `relay_message` in its response envelope.

3. **Deterministic CLI (`personal_archive.py`)**:
   - Owns persistence, sequence allocation, atomic writes, hashes, deduplication, soft deletion, and event history.

### Response contract

The dedicated agent returns a standard JSON response envelope:

```json
{
  "ok": true,
  "source": "personal-archive",
  "operation": "search",
  "status": "found",
  "record_id": "ARCHIVE-20260920-0001",
  "relay_message": "The toaster is a Breville model BTA820XL (Archive ID: ARCHIVE-20260920-0001).",
  "facts": { "brand": "Breville", "model": "BTA820XL" },
  "evidence": [
    { "attachment_id": "ARCHIVE-ATTACH-20260920-0001", "fact": "model", "value": "BTA820XL", "source": "receipt.pdf" }
  ]
}
```

When `main` receives this completion event, it relays `relay_message` directly to the user without altering, questioning, or reconciling it against conversational memory.

## 10. Mutation protocol

This is a critical boundary between probabilistic model behavior and durable state.

For every mutating operation:

    user intent
        ↓
    model builds operation/spec
        ↓
    CLI validates
        ↓
    CLI mutates durable state atomically
        ↓
    CLI returns machine-readable JSON
        ↓
    model parses result
        ↓
    only `ok: true` permits a success message

A temp file is not a commit.
A plausible-looking ID is not a commit.
A model's recollection of a previous command is not a commit.

If validation fails:
1. inspect the actual error;
2. repair only what is justified;
3. rerun;
4. inspect the new result;
5. report success only if the rerun succeeded.

## 11. Mutation response design

Small local models are more reliable when tool results are concise.

Mutation commands should prefer small envelopes, e.g.:

    {
      "ok": true,
      "operation": "create",
      "id": "ARCHIVE-20260920-0001",
      "title": "TestCo toaster",
      "path": "/.../records/ARCHIVE-20260920-0001",
      "attachments_added": []
    }

Detailed record state belongs in `show` or another explicit read operation.

Failure responses should be unambiguously unsuccessful and contain actionable error data.

## 12. Atomicity and filesystem safety

Correctness-critical writes should be atomic where practical:
- write temporary file in appropriate filesystem/location;
- fsync if warranted by durability requirements;
- rename/replace atomically;
- do not leave half-written JSON as normal state.

Sequence allocation must avoid accidental ID reuse.

Attachment copy should avoid destructive moves of the user's source file.

## 13. Attachment handling

On ingest:
- generate stable attachment ID;
- compute SHA-256;
- copy the original into the entity attachment directory;
- preserve useful original filename/type metadata;
- detect duplicates when appropriate;
- associate derived facts with their evidence source.

Deduplication must not cause loss of provenance. The same bytes can be relevant to multiple
events/entities; decide whether physical dedup and logical association are separate concerns.

## 14. Search strategy

The first implementation may use deterministic lexical search. This is acceptable and easy
to inspect.

Future/optional retrieval may combine:
- lexical search
- metadata/fact matching
- aliases/keywords
- local embeddings
- recency
- attachment extracted text

Search/indexes are derived infrastructure. Losing an index must not lose archive data.

The model should receive a bounded candidate set.

## 15. OpenClaw memory boundary

OpenClaw's normal conversational memory and Personal Archive serve fundamentally different purposes.

Normal conversational memory:
- conversational preferences
- user style context
- ephemeral summaries and chat recollections

Personal Archive:
- durable personal records
- source evidence
- receipts/photos/documents
- provenance
- historical changes

### Isolation mechanism

To ensure Personal Archive factual reasoning is never contaminated by chat history or conversational memory:

1. **Context & State Isolation**:
   Personal Archive runs as a separately configured OpenClaw agent (`archivist`). This is an OpenClaw context and state boundary intended to eliminate prompt contamination, not an adversarial OS hypervisor boundary.
2. **Memory Configuration**:
   - `agents.entries.archivist.memory.search.rememberAcrossConversations: false`.
   - Tool denial: `tools.deny: ["group:memory"]` removes `memory_search` and `memory_get` entirely.
   - Workspace isolation: `~/.openclaw/workspaces/archivist/` contains no `MEMORY.md`, `USER.md`, or `memory/` directory.
3. **Active Memory Scoping**:
   If the OpenClaw `active-memory` plugin is active on the Gateway, it is explicitly configured with `config.agents: ["main"]` so `archivist` is never targeted for pre-turn memory retrieval injections.
4. **Dreaming**:
   Dreaming operates on persistent workspaces with memory backends. The `archivist` agent lacks `MEMORY.md` and runs one-shot subagent tasks, remaining outside dreaming sweeps.
5. **Authoritative Principle**:
   If Personal Archive does not have a fact recorded, the agent must report it as not found. It must never fall back to main agent conversational memory.

## 16. Apple Photos integration

### Purpose

Provide convenient visual browsing of archive images.

### Album

Use a regular Photos album:

    Personal Archive

Sharing is outside the initial v1 scope.

### Ownership and safety

A Photos item is managed by Personal Archive only if the system can positively identify it as
such, ideally through the stable `ARCHIVE-ATTACH-...` attachment ID stored as a keyword/metadata value.

Never delete a Photos item merely because it is in an album with a matching name.

### Metadata

Useful projected metadata can include:
- archive title
- description/caption
- Personal Archive entity ID
- Personal Archive attachment ID
- selected brand/model/keywords

### Synchronization

Normal operation:
- write-through import when practical;
- periodic reconciliation to repair drift.

Disaster recovery:
- purge/rebuild only Personal Archive-owned projection assets;
- re-import from authoritative archive.

Do not make nightly destructive rebuilds the default.

## 17. Privacy/security boundary

The code repository is designed to be public.

Therefore:
- no personal absolute home-directory paths;
- use `$HOME`, `~`, configuration, or platform APIs;
- no real archive fixtures;
- no personal contact data;
- no production logs;
- no credentials;
- no screenshots/messages containing personal data.

Use `<archive-root>` in documentation rather than a specific archive location.

Before public commits, inspect staged changes for personal data.

## 18. Deployment topology

A standard deployment topology is:

    M5 development machine
    ~/src/openclaw-personal-archive/ (or local checkout)
              ↓ git push
            GitHub
              ↓ git pull
    M1 OpenClaw host
    ~/src/openclaw-personal-archive/
              ↓ install.sh / openclaw agent config
    ├── ~/.openclaw/workspaces/archivist/          (dedicated agent workspace)
    │   ├── AGENTS.md                             (isolated bootstrap directives)
    │   └── IDENTITY.md                           (isolated persona)
    └── ~/.openclaw/workspace/skills/personal-archive/ (installed skill)

The authoritative personal archive remains on the OpenClaw host outside this repository:

    ~/Documents/OpenClaw/PersonalArchive  (configured as PERSONAL_ARCHIVE_ROOT)

The repository must not contain any personal archive data.

This topology is guidance, not a hard-coded assumption. The software should remain portable.

## 19. Testing architecture

Tests should be able to redirect the archive root to a temporary directory.

No automated test should:
- mutate the real archive;
- touch a real Photos library unless explicitly running a guarded integration test;
- depend on a developer username;
- depend on an existing OpenClaw installation.

Prefer unit/integration tests around the CLI and filesystem contract.

Photos behavior should have dry-run and/or an injectable adapter boundary where practical,
so core safety can be tested without deleting/importing real media.

## 20. First known integration failure

The first synthetic OpenClaw test said:

    Save this in the Personal Archive. I bought a test toaster today.
    The brand is TestCo and the model is TEST-123.

The model staged a spec under `/tmp`, encountered/handled a spec issue, but failed to
reliably complete and verify the create operation before claiming success.

Manual execution of the CLI then successfully created:

    ARCHIVE-20260920-0001

The erroneous agent message had presented a differently formatted invented path/ID.

The real record also stored no structured event date despite the unambiguous word "today."

This failure motivates the v1.1 priorities:
- verified mutation protocol;
- no invented IDs;
- concise CLI results;
- relative-date normalization;
- regression tests.

## 21. Evolution principles

When extending the archive:

1. Preserve old evidence.
2. Prefer migrations over silent schema breakage.
3. Keep IDs stable.
4. Keep derived systems rebuildable.
5. Favor explicit provenance.
6. Favor reversible changes.
7. Make destructive operations obvious and guarded.
8. Design for small model context.
9. Put correctness-critical behavior in code.
10. Test real bugs as regressions.
