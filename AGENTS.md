# AGENTS.md — OpenClaw Home Archive

This file is the durable engineering handoff for coding agents working in this repository.
Read it before changing code. Also read `docs/ARCHITECTURE.md`, `SKILL.md`, and the relevant
implementation/tests before making changes.

## Project purpose

OpenClaw Home Archive is an OpenClaw skill for casually capturing and later retrieving
long-lived household information and source evidence.

Typical user interactions should feel conversational:

- "Save this, it's the new lawnmower."
- "This is the receipt for the water heater."
- "Here's Joe's business card. He's the guy who built our deck."
- "What toaster do we have and when did we get it?"
- "Show me the business card for the person who built the deck."
- "What size furnace filter do I need?"
- "Send me everything I gave you about the deck."

The user should not have to design a database schema, choose categories, know archive IDs,
or invoke CLI commands directly. The model interprets natural language; deterministic code
owns durable storage and mutation mechanics.

## Current status

This project is experimental/pre-release.

The repository began as a working prototype. The underlying CLI successfully created a
record during manual testing, but the first OpenClaw end-to-end integration test exposed
an important orchestration failure: the agent wrote a temporary JSON spec, attempted a
create, repaired the spec, then claimed archival success without successfully rerunning
and verifying the CLI operation. It also reported an invented/malformed archive path/ID.

Treat this as a high-priority correctness issue. A natural-language success message is not
proof that a mutation happened.

## Non-negotiable invariants

### 1. The on-disk archive is authoritative

The durable Home Archive is the source of truth.

Configured root (`HOME_ARCHIVE_ROOT` environment variable):

    <archive-root>

`<archive-root>` is a documentation placeholder for the chosen absolute archive path
outside this repository. Pass the configured environment to every CLI invocation.
There is no fallback location. The installer persists the user's choice under
`skills.entries.home-archive.env.HOME_ARCHIVE_ROOT` in OpenClaw configuration.

Do not make OpenClaw conversational memory, an embedding index, Apple Photos, temporary
files, or model-generated summaries authoritative.

### 2. Never put household data in this repository

This repository contains software and documentation only.

Never commit:
- real archive records
- household photos
- receipts
- warranty documents
- message exports
- contact cards from real people
- logs containing private messages
- `.env` files
- credentials, tokens, API keys, Apple IDs, phone numbers, or other personal identifiers

Tests must use synthetic/disposable data and preferably a temporary archive root.

### 3. A temporary spec is not an archived record

Writing `/tmp/...json` or any other intermediate spec is merely staging.

For every mutation:
1. construct/validate the requested operation;
2. invoke `home_archive.py`;
3. parse its JSON result;
4. require `ok: true`;
5. only then report success to the user.

If the CLI rejects input and the agent repairs the input, it MUST rerun the CLI and inspect
the new result. Repairing a spec without rerunning the mutation is failure.

### 4. Never invent durable identifiers or paths

Entity IDs (`HA-...`) and attachment IDs (`HAA-...`) are generated by deterministic code.

The model must never infer, predict, reconstruct, or fabricate them.

For create/add/update/delete/merge operations, user-facing IDs and paths must come from
successful CLI output or a subsequent verified read/search.

Current entity ID shape is approximately:

    HA-YYYYMMDD-NNNN

Do not silently change the ID format. Existing IDs are durable identifiers.

### 5. Preserve original evidence

Original attachments are evidence and should be copied into the archive and preserved.
Extracted text, OCR, vision descriptions, model numbers, dates, and other derived facts may
be wrong. They must not replace the original source.

### 6. Facts need provenance

Where practical, extracted facts should record where they came from and confidence, e.g.:

    model = BTA820XL
    source = IMG_1036.jpg
    confidence = high

or:

    deck_completion_date = 2026-09-20
    source = user

This enables later questions such as "How do you know?" and "Show me where that model
number came from."

### 7. Prefer deterministic code for correctness-critical mechanics

Code should own:
- IDs and sequence allocation
- filesystem layout
- atomic writes
- event history
- attachment copying
- SHA-256 hashing/deduplication
- merge mechanics
- soft deletion/trash
- provenance persistence
- validation
- deterministic search mechanics
- Photos synchronization/reconciliation
- safety checks

The model should own fuzzy interpretation:
- archive intent
- entity matching
- natural-language understanding
- useful fact extraction
- image/document understanding
- conversational retrieval and presentation

Move behavior into deterministic code when doing so materially reduces hallucination or
data-loss risk.

### 8. Keep model context small

Do not solve archive retrieval by loading the entire archive into the model context.
Use deterministic search/indexing to narrow candidates, then provide only relevant records
and evidence to the model.

Mutation CLI responses should also be concise and machine-friendly. Do not return a giant
record when the caller only needs proof of success and identifiers.

### 9. Conservative entity linking

Wrongly attaching evidence to an existing entity is worse than creating a duplicate.

When evidence could plausibly belong to multiple records, the conversational layer should
ask the user rather than silently choosing. Duplicate records can later be merged.

### 10. Destructive actions require stronger safeguards

Prefer reversible operations:
- fact removal preserves history
- attachment removal is soft/reversible when possible
- entity deletion moves to trash / marks deleted
- permanent purge requires explicit user confirmation

Do not weaken these protections casually.

### 11. Apple Photos is a projection

The regular Photos album named `Home Archive` is a human-facing materialized view, not the
database.

Nothing important may exist only in Photos.

Home Archive code may delete only Photos assets it can prove are managed by Home Archive.
Never delete arbitrary assets from the user's Photos library.

A managed Photos asset should carry a stable Home Archive attachment identifier (`HAA-...`)
in metadata/keywords so synchronization and rebuild can match it safely.

Prefer incremental/write-through synchronization plus reconciliation. A full purge/rebuild
is disaster recovery, not the normal daily sync strategy.

## Expected archive model

An archive entry is a persistent entity that accumulates evidence over time. It is not just
the message that created it.

Example:
- User says: "Just had this deck built today. Builder was Joe from Example Decks."
- Later: "Here's Joe's business card. He's the guy who built our deck."

Those should normally become one durable deck entity with multiple events, facts, and
attachments, provided the association is unambiguous.

Conceptual record layout:

    <archive-root>/
    ├── README.md
    ├── records/
    │   └── HA-20260920-0007/
    │       ├── record.md
    │       ├── metadata.json
    │       ├── events.jsonl
    │       └── attachments/
    ├── trash/
    └── state/
        └── sequence.json

`metadata.json` is structured current state.
`events.jsonl` preserves history.
`record.md` is a convenient human/model-readable current view, not the sole database.
Attachments preserve original evidence.

## Relative dates

The conversational layer should resolve unambiguous relative dates using the user's/local
current date available at execution time.

Examples:
- "I bought this toaster today." -> structured purchase/event date for that local date.
- "The deck was finished yesterday." -> previous local calendar date.

Preserve the original user wording in notes/events as evidence as well.

Do not invent dates when the reference is ambiguous or current local date/time is not
reliably known. Ask or omit the structured date rather than guessing.

## CLI design expectations

The CLI currently lives at:

    scripts/home_archive.py

It exposes operations including:

    init
    create --spec ...
    add HA-... --spec ...
    search "..."
    show HA-...
    get-attachment HAA-...
    set-fact HA-... --key ... --value ...
    remove-fact HA-... --key ...
    remove-attachment HAA-...
    delete HA-...
    merge HA-CANONICAL HA-DUPLICATE
    photos-sync [--dry-run]
    photos-rebuild [--dry-run|--confirm]
    doctor

Preserve compatibility unless there is a compelling reason not to.

For mutation success, prefer a compact response similar to:

    {
      "ok": true,
      "operation": "create",
      "id": "HA-20260920-0001",
      "title": "TestCo toaster",
      "path": ".../records/HA-20260920-0001",
      "attachments_added": []
    }

The exact schema can evolve deliberately, but callers need an unambiguous success flag and
the authoritative IDs produced by the CLI.

On failure, return a non-success result and useful error information. Do not emit output
that a small model could easily mistake for success.

## Known first integration regression

Synthetic test input:

    "Save this in the Home Archive. I bought a test toaster today.
     The brand is TestCo and the model is TEST-123."

Observed manual CLI creation produced a real ID:

    HA-20260920-0001

The earlier agent response incorrectly claimed a path containing:

    HA-2026-09-20-0001

The real created record also had `event_date: null` even though "today" was unambiguous in
the interaction.

Regression coverage should ensure:
- CLI IDs are the only IDs surfaced;
- successful mutation output is compact and authoritative;
- malformed/invalid specs cannot lead to apparent success;
- repaired specs must be followed by a real mutation invocation;
- relative-date behavior is documented/testable at the appropriate layer;
- archive mutations can be tested against an isolated temporary root.

## Testing expectations

Before considering a change complete:
1. run syntax/static checks available in the repo;
2. run automated tests;
3. use temporary/disposable archive data;
4. test failure paths, not only happy paths;
5. inspect generated filesystem state where relevant;
6. ensure no private/archive data has entered Git;
7. report what was run and whether it passed.

Add regression tests whenever a real integration bug is found.

Useful test categories:
- init/idempotent init
- ID allocation
- create
- add evidence
- fact updates/supersession
- remove fact
- attachment copy/hash/dedup
- attachment lookup
- soft delete
- merge
- search
- malformed specs
- nonexistent IDs
- atomicity/interrupted writes where practical
- doctor
- Photos dry-run/safety behavior where testable without touching a real Photos library

Tests must never mutate a developer's real archive. Set `HOME_ARCHIVE_ROOT` to an
isolated temporary directory for test CLI invocations.

## Working style for coding agents

Before editing:
1. read this file;
2. read `docs/ARCHITECTURE.md`;
3. read `SKILL.md`;
4. inspect the implementation and tests;
5. state any assumption that would change persisted data or compatibility.

While editing:
- make focused changes;
- preserve backward compatibility where reasonable;
- do not refactor unrelated code just for style;
- favor clear schemas and deterministic behavior;
- keep platform-specific Photos code isolated;
- make filesystem operations testable with an overridden root.

After editing:
- run tests;
- show a concise diff summary;
- call out migrations or compatibility implications;
- do not commit unless explicitly asked.
